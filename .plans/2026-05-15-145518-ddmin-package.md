# DDMin Package Plan

## Goal

Implement a small standalone `ddmin` algorithm crate for fixture3.

This plan does not connect `ddmin` to fixture reduction, filesystems, TOML, Rust source, manifests, or CLI commands.

The goal is a deterministic generic reducer over an ordered candidate list and a tri-state oracle.

## Non-Goals

- Do not implement fixture-tree reduction in this plan.
- Do not implement TOML reduction in this plan.
- Do not implement source-code reduction in this plan.
- Do not implement Perses, ProbDD, WDD, CDD, HDD, DFS, BFS, slicers, or parallel reducers.
- Do not depend on GPL code.
- Do not copy Perses source code.
- Do not add Rust unit tests, integration tests, doc tests, inline `#[test]`, or a `tests/` directory.

- temp directories
- proof file serialization
- candidate dependency closure

## Public Contract

Use this contract as the crate API.

The names can change during implementation only if the semantics stay identical.

```rust
pub struct DdminInput<C> {
    pub candidates: Vec<C>,
    pub options: DdminOptions,
}

pub struct DdminOptions {
    pub initial_granularity: NonZeroUsize,
    pub max_oracle_calls: Option<usize>,
}

pub enum OracleOutcome {
    Interesting,
    NotInteresting,
    Unresolved(UnresolvedReason),
}

pub enum UnresolvedReason {
    Timeout,
    MaterializationFailed,
    OracleFailed,
    InvalidCandidateSet,
    NonDeterministic,
}

pub trait DdminOracle<C> {
    fn evaluate(&mut self, remaining: &[C]) -> OracleOutcome;
}

impl<C, F> DdminOracle<C> for F
where
    F: FnMut(&[C]) -> OracleOutcome,
{
    fn evaluate(&mut self, remaining: &[C]) -> OracleOutcome {
        self(remaining)
    }
}

pub struct DdminOutput<C> {
    pub remaining: Vec<C>,
    pub removed: Vec<C>,
    pub stats: DdminStats,
    pub guarantee: DdminGuarantee,
}

pub struct DdminStats {
    pub oracle_calls: usize,
    pub interesting_trials: usize,
    pub not_interesting_trials: usize,
    pub unresolved_trials: usize,
}

pub enum DdminGuarantee {
    OneMinimalWithinCandidateSet,
    Incomplete(DdminStopReason),
}

pub enum DdminStopReason {
    MaxOracleCallsReached,
    BaselineNotInteresting,
}

pub fn ddmin<C, O>(
    input: DdminInput<C>,
    oracle: &mut O,
) -> DdminOutput<C>
where
    C: Clone + Eq,
    O: DdminOracle<C>;
```

The oracle is the callback.

`ddmin` cannot decide whether a candidate list is interesting. It only proposes smaller `remaining` lists. The caller evaluates each proposed list against the real system and returns `OracleOutcome`.

Example caller shape:

```rust
let mut oracle = |remaining: &[CandidateId]| {
    let materialized = materialize_candidate_set(remaining);
    match materialized {
        Ok(workspace) if fixture_contract_passes(&workspace) => OracleOutcome::Interesting,
        Ok(_) => OracleOutcome::NotInteresting,
        Err(reason) => OracleOutcome::Unresolved(reason),
    }
};

let output = ddmin(input, &mut oracle);
```

For this standalone crate, the real-system work above is out of scope. The crate only calls the callback and reacts to the result.

## Input Semantics

- `candidates` is the full ordered candidate set.
- The oracle receives the current remaining candidate list.
- A candidate absent from `remaining` is treated as removed.
- Candidate order is preserved.
- The algorithm must not reorder candidates.
- The algorithm must not synthesize candidates.
- Duplicate candidate values are allowed only when `C` itself is a stable unique ID.
- Fixture3 callers should pass `CandidateId`, not raw paths or raw TOML keys.

## Output Semantics

- `remaining` is the reduced candidate list that still returns `Interesting`.
- `removed` is `input.candidates - remaining`, computed by candidate identity.
- `Unresolved` is never accepted as a successful reduction.
- `NotInteresting` is never accepted as a successful reduction.
- If the baseline `oracle.evaluate(&input.candidates)` is not `Interesting`, the reducer stops with `Incomplete(BaselineNotInteresting)`.
- If `max_oracle_calls` is reached, the reducer stops with `Incomplete(MaxOracleCallsReached)`.
- `OneMinimalWithinCandidateSet` means no single remaining candidate was removable by the completed algorithm under this oracle and candidate model.
- `OneMinimalWithinCandidateSet` does not mean global minimality.
- `OneMinimalWithinCandidateSet` does not mean semantic minimality outside the oracle.

## Oracle Semantics

- `Interesting` means the candidate list still preserves the property being reduced for.
- `NotInteresting` means the candidate list lost the property.
- `Unresolved` means the caller could not validly evaluate the candidate list.
- The algorithm treats `Unresolved` as not accepted for reduction.
- The algorithm counts `Unresolved` separately because unresolved trials indicate adapter or oracle fragility.
- The algorithm must not inspect candidate content.
- The algorithm must not infer filesystem, syntax, or test behavior.
- The callback must be deterministic for a given `remaining` list if the caller wants a meaningful guarantee.

## Algorithm Decision

Implement canonical `ddmin` as the first and only algorithm.

Use the classic granularity loop:

1. Start from the full candidate list.
2. Verify the full candidate list is `Interesting`.
3. Split the current list into `n` contiguous partitions.
4. Try each partition alone.
5. If a partition is `Interesting`, replace the current list with that partition and reset `n = 2`.
6. Try each complement of one partition.
7. If a complement is `Interesting`, replace the current list with that complement and set `n = max(n - 1, 2)`.
8. If no partition or complement is `Interesting`, set `n = min(2 * n, current_len)`.
9. Stop when no further split can be made.

The implementation must treat `Unresolved` the same as "not accepted", but count it separately.

## Implementation Rules

- Implement from the contract, paper semantics, and behavior fixtures.
- Use Perses as a checklist for engineering decisions, not as source material.
- Keep the implementation small enough to audit directly.
- Keep all filesystem and fixture behavior outside this module.
- Make every oracle call observable through `DdminStats`.
- Preserve deterministic candidate order.
- Do not cache oracle calls in the first implementation unless repeated calls appear in fixture verification output.
- Do not parallelize.

## Edge Cases

The module must define behavior for:

- empty input
- one candidate
- two candidates
- odd-sized lists
- duplicate-looking candidate labels represented by unique IDs
- oracle baseline returning `NotInteresting`
- oracle baseline returning `Unresolved`
- every trial returning `NotInteresting`
- some trials returning `Unresolved`
- `max_oracle_calls` reached before fixpoint
- candidate list where only a complement is interesting
- candidate list where only a partition is interesting

## Verification Model

Do not add Rust tests unless the repository policy changes.

Add behavior fixtures later under the fixture3 verification model.

Fixtures for this standalone algorithm must cover:

- baseline input satisfies the oracle
- baseline input does not satisfy the oracle
- empty candidate set
- one required candidate
- two required candidates
- multiple required candidates
- duplicate labels with unique IDs
- order-preserving subsequences
- non-monotonic oracle behavior
- unresolved trials are not accepted
- no removable candidate at fixpoint
- max oracle calls stops with `Incomplete(MaxOracleCallsReached)`
